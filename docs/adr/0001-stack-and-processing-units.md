# ADR 0001: 技術スタックと処理単位による構成

- 日付: 2026-10-06
- 関連 Issue: [#2 アーキテクチャ境界と依存方向を決定する](https://github.com/sakashita44/caption-weave/issues/2)

CaptionWeave の実装言語、UI、主要ライブラリと、コードを処理単位で区分する構成を定める。各処理単位の内部設計と具体値（キュー容量、再試行回数、保持行数など）は、対応する実装 Issue で決める。

## 前提条件

この決定は次の前提に基づく。いずれかが変更された場合は、この ADR を見直す。

- 対象環境として Windows x64 を必須とする。Linux と macOS は動作することが望ましいが、必須とはしない
- 主な利用場面は大学研究室の発表であり、日本語の発表には英語字幕を、英語の発表には日本語字幕を付与する。翻訳方向は利用者がセッション開始時に選び、言語の自動判別は行わない
- 主な利用者は発表者であり、投影画面の上に最前面で字幕バーを重ねて使用する。聴衆が手元の端末で使う場合もある
- 音声認識は端末内で行い、翻訳は Gemini API で行う。配布物は portable ZIP とする
- 開発と保守は一人で行う

## 技術スタック

| 用途           | 採用                                                                                                     |
| -------------- | -------------------------------------------------------------------------------------------------------- |
| 言語と実行基盤 | C# / .NET 10（LTS）                                                                                      |
| UI             | WPF                                                                                                      |
| 音声取得       | NAudio（WASAPI のマイク入力と loopback）                                                                 |
| 音声認識       | sherpa-onnx、Vosk（公式 NuGet）、Moonshine（公式 C API を P/Invoke で接続）。採用エンジンは #13 で決める |
| 翻訳           | HttpClient による Gemini API の呼び出し。SDK の採否は #4 で決める                                        |
| API キー保護   | DPAPI（CurrentUser スコープ）                                                                            |
| 配布           | 自己完結形式の publish を ZIP 化する                                                                     |

C# / .NET を採用した理由は次のとおり。

- 長時間のリアルタイム処理を、非同期ストリームと容量付きキューで安定して実装できる
- WASAPI と DPAPI を、外部ライブラリを追加せずに利用できる
- 自己完結 publish により、管理者権限もランタイムの事前導入も不要な ZIP を作成できる
- 音声認識の候補 3 系統のうち 2 系統に公式の .NET パッケージがあり、残る Moonshine も C API から接続できる。先行アプリである [moon-live-captions](https://github.com/yukkes/moon-live-captions)（MIT）は、C# から Moonshine の C API を P/Invoke で呼び出す実装を含む。コードを移植するかどうかは #7 で決める

WPF を採用した理由は、Windows での実績が十分にあるためである。類似製品である [LiveCaptions-Translator](https://github.com/SakiRinn/LiveCaptions-Translator) と moon-live-captions は、いずれも WPF で字幕ウィンドウを実装している。字幕バーに必要な非アクティブ化やクリック透過の挙動は、Avalonia を選んでも Win32 API を直接呼び出す必要があり、Windows 向けの実装量は減らない。Linux 対応が必須ではない前提において、Avalonia のクロスプラットフォーム性よりも Windows での確実さを優先した。

Python は認識エンジンの選択肢が最も広いものの、GIL による並行処理の制約や、数百 MB に達する配布物の扱いが不利となる。Rust + Tauri や C++ + Qt は、認識エンジンの接続とビルド環境の整備において、一人で開発・保守する負担が大きい。

## 処理単位

コードは技術的な層ではなく処理の役割に応じて区分する。一つの処理に関わる要素（キュー、再試行、外部 API クライアントなど）を同じ区分に収め、処理の変更時に参照するコードの範囲を局所化するためである。

| 処理単位     | 入力と出力                                                 | 含むもの                                                                                |
| ------------ | ---------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| 文字起こし   | PCM の列を受け取り、発話ごとの partial と final の列を返す | エンジンごとのアダプター、VAD（発話境界を自前で検出しないエンジンのみ）、発話 ID の採番 |
| 翻訳         | 確定した原文の列を受け取り、訳文、スキップ、失敗の列を返す | 容量付きキュー、文脈と用語、再試行、Gemini クライアント                                 |
| 字幕         | 文字起こしと翻訳をつなぎ、表示用の字幕行を管理する         | セッション、原文と訳文の対応付け、古いセッションの結果の破棄、保持行数の上限            |
| アプリ本体   | 利用者の操作と表示、各処理単位の組み立てを担う             | 音声取得、字幕バーの表示、ウィンドウ制御、DPAPI、設定                                   |
| ベンチマーク | 文字起こしだけを使い、受入測定を行う                       | 固定 WAV と実時間速度の入力、指標の算出                                                 |

### プロジェクトへの配置

処理単位は名前空間とフォルダで区分する。プロジェクトとして独立させる対象は、複数の実行入口から利用されるものと、実行入口そのものに限る。

| プロジェクト                              | 収める処理単位         | 独立させる理由                             |
| ----------------------------------------- | ---------------------- | ------------------------------------------ |
| `CaptionWeave.Transcription`（`net10.0`） | 文字起こし             | アプリ本体とベンチマークの両方から利用する |
| `CaptionWeave.App`（`net10.0-windows`）   | 字幕、翻訳、アプリ本体 | アプリの実行入口                           |
| `CaptionWeave.Bench`（`net10.0`）         | ベンチマーク           | 測定用の実行入口                           |
| `CaptionWeave.Tests`                      | テスト                 | テストの実行単位                           |

字幕と翻訳は Windows に依存しないが、利用元がアプリ本体のみであるため、`CaptionWeave.App` に収める。Linux 対応が必要になった時点で、両者を Windows に依存しないプロジェクトへ移す。

### 処理単位の境界

処理単位間に設けるインターフェースは、文字起こしと翻訳の 2 つに限る。

- 文字起こし: PCM の列を受け取り、認識イベントの列を返す。認識イベントは、発話 ID、partial と final の別、本文を含む。エンジンの交換、ベンチマークでのエンジンの切り替え、字幕のテストでの差し替えに用いる
- 翻訳: 確定した原文の列を受け取り、発話ごとの結果（訳文、スキップ、失敗）の列を返す。字幕のテストでの差し替えに用いる

音声入力にはインターフェースを設けない。アプリ本体は NAudio から、ベンチマークは WAV からそれぞれ PCM の列を生成して文字起こしへ渡す。翻訳の内部にもインターフェースを置かない。再試行やタイムアウトのテストは、HttpClient の `HttpMessageHandler` を差し替えて行う。

## 字幕処理の方針

- 原文は認識イベントを受け取った時点で字幕行へ反映し、訳文は翻訳結果が届いた時点で同じ字幕行へ反映する。応答の順序が前後しても、発話 ID で字幕行を対応付ける
- 翻訳対象は final に限る。ライブ字幕では新しい発話の訳ほど価値が高いため、翻訳キューには容量の上限を設け、上限に達した場合は待機中で最も古い発話の翻訳をスキップとして破棄する
- 翻訳の失敗は字幕行の状態として記録し、原文の表示と音声認識は継続する。認証失敗のように利用者の対処が必要な失敗は、利用者へ通知する
- セッションの開始ごとに新しいセッション ID を発行し、直前のセッションをキャンセルする。キャンセルが間に合わずに届いた結果は、字幕行への反映前と画面への描画前にセッション ID を照合して破棄する
- 字幕は、直近の字幕行の内容が更新されたことを通知する。アプリ本体は描画頻度を抑えて最新の状態を画面へ反映する
- 保持する字幕行と音声入力のバッファには上限を設ける。音声入力が上限を超えた場合は、暗黙に破棄せず欠落として記録し、利用者へ通知する
- 認識イベントは時刻を含まない。ベンチマークは、イベントを受け取った時刻を自身で記録し、正解データの発話区間と照合して遅延を算出する

## 採用しなかった構成

- Presentation、Application、Domain、Infrastructure、Platform の各層を別プロジェクトにする構成: 技術的な区分であり、翻訳キューや再試行など一つの処理に関わる要素が複数のプロジェクトに分散するため
- 認識エンジンごとに別プロジェクトにする構成: アプリ本体は採用エンジンの決定後に実装するため、採用しなかったエンジンのコードを決定時に削除すれば配布物から除外できるため
- 実行時に DLL を読み込むプラグイン機構、イベントバス、翻訳の並列実行: 対応する要求がないため
